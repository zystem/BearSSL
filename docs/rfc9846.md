# RFC 9846 against this fork

*Kind: record.* [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html) (July 2026) obsoletes RFC 8446, the specification the TLS 1.3 code was written to. This page says what changed and where the code stands. Checked on 2026-11-28 at commit `beea7d3`; what was found not met was then changed the same day, and this page shows the code after the change.

**The fork does not claim conformance to RFC 9846.** Some requirements are not met (below).

## Method, and its limits

- The list of technical changes in RFC 9846 section 1.2.
- The sentences of RFC 9846 with MUST, SHOULD, MAY, REQUIRED or RECOMMENDED that have no close match in RFC 8446 (79 of 452, word overlap below 75 %), read one by one. Many are editorial.
- The code, read; and throwaway probes on Linux x86-64 (an engine given changed or injected records; peers with a changed handshake source that break the record boundary at a key change). The probes are not in the repository; what was fixed after them is held by the test `TLS13_ALERTS`.
- This is **not** a requirement-by-requirement audit of RFC 9846. Changed text without those key words was not compared, and the errata were not read.

In the tables: **probe** was run, **test** names a group of `testcrypto`, **reading** means the code was read and nothing was run.

## The changes of section 1.2

| Change | Here | How known |
|---|---|---|
| A key share is not reused between connections | Met: each handshake makes its own key | reading |
| TLS 1.0 and 1.1 are not negotiated | **Partly**: the profile functions set a minimum of TLS 1.2 since 2026-11-28; `brssl` too. A program can still allow them with `br_ssl_engine_set_versions()`, a user of `brssl` with `-vmin` | reading |
| Which hash goes with a PSK after a HelloRetryRequest | Met: the binder is computed as section 4.3.11 says; the client keeps offering the PSK, which the RFC allows. A PSK whose hash differs from the suite of the HelloRetryRequest was not tried | reading |
| A client that does not support resumption ignores NewSessionTicket | Does not apply: the client supports it. Unknown extensions of the message are skipped | reading |
| The key is changed before the usage limit (now MUST) | Met | test `TLS13_KEYUPDATE` |
| A limit on KeyUpdate: the sender does not pass 2^48-1 key changes | **Not met as written**: there is no counter. Reaching the number is not practical | reading |
| No second `update_requested` before the peer answered the first | Met: the engine never asks the peer to update | reading |
| `close_notify` is sent as a warning | Met | reading |
| `user_canceled` is ignored and followed by `close_notify` | Met: never sent; ignored at either level until the `close_notify` | test `TLS13_ALERTS` |
| New alert `general_error` | Never sent; received, it ends the connection | probe |
| CertificateRequest may have an empty extension list (syntax) | A request without `signature_algorithms` is refused, as it must be, with `missing_extension` | reading |
| Bounds of the ClientHello and NewSessionTicket extension lists (syntax) | Met | reading |
| Wording on KEMs, the transcript hash, RSA-PSS ([RFC 9963](https://www.rfc-editor.org/rfc/rfc9963.html)), "master" renamed "main" | Nothing changes on the wire. The names in the API and the comments still say "master" | reading |

| 1 | 4.3 | A known extension in a message where it does not belong: `illegal_parameter` | Done for the cases in [reference-api.md](reference-api.md), "Alerts on errors". The client still answers `unsupported_extension` for other known types, and does not look into the extensions of certificates |

## Choices

- ChangeCipherSpec (section 5): every one before the peer's Finished is dropped, as the RFC says. A client does **not** accept one that comes before the ServerHello, although the text allows it after the ClientHello (by reading).
- The version of a record header (section 5.1) is ignored for unprotected records. A protected record with another version than 0x0303 is refused with `protocol_version`, where the RFC says to ignore the field: the field is not otherwise checked, since the engine builds the additional data with 0x0303.

## Not applicable

Requirements about 0-RTT, external PSKs, post-handshake client authentication and TLS 1.2: the fork has none of the first three ([supported-versions.md](supported-versions.md)), and the TLS 1.2 code is that of upstream.
